
# 设计思想
## 整体结构
libuv 是跨平台，事件驱动，异步I/O库。

除了提供事件驱动外，还提供一些常用工具:
例如定时器，非阻塞的网络支持，异步文件系统访问，子进程等。

## Event loops
在事件驱动编程中，程序会关注每一个事件，并且对每一个事件的发生做出反应。
libuv会负责将来自操作系统的事件收集起来，或者监视其他来源的事件。
这样，用户就可以注册回调函数，回调函数会在事件发生的时候被调用。event-loop会一直保持运行状态。用伪代码描述如下：
```bash
while 进程有待处理的事件
    e = 返回一个事件
    if 存在事件e相关的回调
        执行回调
```

Event Loops特点
- 非阻塞IO
  - 所有底层IO都使用非阻塞IO

- 线程绑定与安全性
  - 单线程绑定：每个事件循环必须绑定到单个线程，不能跨线程共享；但支持同时运行多个事件循环（需确保每个循环在独立线程中）。
  - 非线程安全：除非 libuv 明确标注，否则与事件循环、句柄（handles）相关的 API 均不支持线程安全，跨线程操作可能导致异常。

- I/O 线程差异：
  - 网络 I/O：全程在事件循环绑定的单线程中执行，无线程池参与；
  - 文件 I/O：因无跨平台异步原生接口，需通过 libuv 全局线程池实现 “异步效果”（底层仍为阻塞 I/O，但由线程池分担，不阻塞事件循环线程）。

- 部分操作offload到线程池
  - 由于跨平台考虑，某些操作没有非阻塞IO原语，为避免主线程阻塞，libuv将这些操作offload到线程池.
  - 有三种操作需要被offload到线程池:
    - **文件系统操作**：如文件读写、创建、删除等阻塞性文件操作；
    - **DNS函数**：`getaddrinfo`（通过域名查IP）和`getnameinfo`（通过IP查域名），这类网络相关的查询本质是阻塞操作，需借线程池异步执行；
    - **用户自定义代码**：开发者可通过`uv_queue_work()`接口，将自定义的阻塞逻辑提交到线程池，避免占用主线程。
  - 性能瓶颈
    - 由于线程池的**默认大小是有限的**（通常不高，如默认4-8个线程），若大量任务同时排队，可能导致操作延迟。需参考“Thread pool work scheduling”章节优化任务调度，避免线程池成为瓶颈。

## Handles 和 Requests
Handle 和 Requests 就是 Event Loops 的 callback

- Handles（句柄）：长生命周期的“持续活动载体”
  - 代表**长期存在**的对象，只要处于“活跃（active）”状态，就能持续执行特定操作
  - 如: **TCP server handle（TCP 服务端句柄）**：启动后持续监听连接，**每有新连接到来**就触发连接回调，直到服务端主动关闭。
- Requests（请求）：短生命周期的“单次操作单元”
  - 代表**临时、短期**的操作，通常对应一次具体的异步任务，任务完成后即结束生命周期。
  - **依附 Handle 的请求**：如 `write request`（写请求），需绑定到某个 Handle（如 TCP 连接句柄），仅用于完成“向该 Handle 写入数据”这一次操作，写完成后请求即失效。

- Handle vs Requests

| 维度         | Handles（句柄）                | Requests（请求）                |
|--------------|--------------------------------|--------------------------------|
| 生命周期     | 长（持续活跃，直到主动关闭）   | 短（单次操作完成即结束）       |
| 功能定位     | 长期承载异步任务的“容器”       | 执行单次异步操作的“单元”       |
| 与 Handle 依赖 | 自身就是独立载体，无需依赖其他 | 要么依附 Handle，要么独立运行  |
| 回调触发频率 | 活跃期间多次触发（如每次循环/新连接） | 仅操作完成后触发一次           |

# 基础
## handle stream request
在 libuv 中，handle、stream 和 request 是三个核心概念，它们构成了异步 I/O 操作的基础架构：

### 1. Handle（句柄）
**作用**：代表长期存在的资源或活动
- 生命周期较长，需要手动初始化和清理
- 与事件循环关联，用于监控特定类型的 I/O
- 示例：`uv_tcp_t`, `uv_udp_t`, `uv_pipe_t`, `uv_timer_t`

```c
// filepath: example.c
uv_tcp_t tcp_handle;
uv_tcp_init(loop, &tcp_handle);  // 初始化
// ... 使用 handle ...
uv_close((uv_handle_t*)&tcp_handle, NULL);  // 清理
```

### 2. Stream（流）
**作用**：处理双向数据流的抽象基类
- 继承自 handle，是 TCP、管道等流式 I/O 的基类
- 提供统一的读写接口：`uv_read_start()`, `uv_write()`
- 示例：`uv_tcp_t`, `uv_pipe_t`, `uv_tty_t` 都是 stream 的子类

```c
// filepath: example.c
uv_stream_t* stream = (uv_stream_t*)&tcp_handle;
uv_read_start(stream, alloc_cb, read_cb);  // 开始读取数据
```

### 3. Request（请求）
**作用**：代表短期的、一次性的操作
- 生命周期短暂，通常在操作完成后立即失效
- 不需要手动清理（操作完成后自动释放）
- 示例：`uv_write_t`, `uv_connect_t`, `uv_getaddrinfo_t`

```c
// filepath: example.c
uv_write_t write_req;
uv_buf_t buf = uv_buf_init("hello", 5);
uv_write(&write_req, stream, &buf, 1, write_cb);  // 一次性写操作
```

### 三者的关系

**层级关系**：
```
Handle (基类)
  └── Stream (流式I/O基类)
       └── TCP/Pipe/TTY (具体实现)
       
Request (短期操作)
```

**使用模式**：
1. 创建 **handle** 来管理长期资源（如 TCP 连接）
2. 通过 **stream** 接口进行数据读写
3. 使用 **request** 执行具体的单次操作（如写入数据）

**内存管理差异**：
- **Handle**：需要显式初始化和关闭
- **Request**：栈上分配，操作完成后自动清理
